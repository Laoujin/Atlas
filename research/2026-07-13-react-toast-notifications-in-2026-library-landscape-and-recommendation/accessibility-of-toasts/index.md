> **TL;DR** — An accessible toast needs five things that almost no library gives you by default: a live region that is **already in the DOM** before the message arrives [[7]](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role), `role="status"` (polite) for everything that isn't an error [[5]](https://www.w3.org/WAI/ARIA/apg/patterns/alert/), a **keyboard route to the toast** (F6/F8/Alt+T landmark hotkey) [[29]](https://react-aria.adobe.com/Toast), a timer that **pauses on focus, not just hover**, and either no auto-dismiss or a duration the user can change [[1]](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html). Of the mainstream React libraries, **[Base UI Toast](https://base-ui.com/react/components/toast)** and **[React Aria Toast](https://react-aria.adobe.com/Toast)** get the model right (non-modal `alertdialog` + landmark + priority split); **[Radix](https://www.radix-ui.com/primitives/docs/components/toast)** ⭐ 19.1k is close but has an open "never announced" bug [[14]](https://github.com/radix-ui/primitives/issues/3634); **[Sonner](https://sonner.emilkowal.ski/)** ⭐ 12.6k is polite-only (your `toast.error()` is never assertive) and defaults to 4 s [[18]](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx); **[react-hot-toast](https://react-hot-toast.com/)** ⭐ 11k is the worst of the group — no persistent live region, no hotkey, toasts not focusable [[26]](https://github.com/timolins/react-hot-toast/blob/main/src/core/toast.ts); **[notistack](https://notistack.com/)** ⭐ 4.1k slams `role="alert"` on a node that mounts already populated [[28]](https://github.com/iamhosseindhv/notistack/blob/master/src/ui/MaterialDesignContent/MaterialDesignContent.tsx) — the one thing MDN explicitly says does not work.

## The three rules everything else follows from

**1. The live region must pre-exist the message.** This is the single most-violated rule in the ecosystem. MDN is blunt: *"Do not try to dynamically add/generate an element with `role="alert"` that is already populated with the alert message you want announced — this generally does **not** lead to an announcement, as it is not a content change."* [[7]](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role) The ARIA APG's own alert example works exactly this way: the alert element is rendered empty at page load and the message is *inserted into it* on trigger [[6]](https://www.w3.org/WAI/ARIA/apg/patterns/alert/examples/alert/). Sara Soueidan states the rule generally: *"place the live region container in the DOM as early as possible and then populate it… This ensures that the live region is monitored for updates before they happen."* [[8]](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1/)

A React toast library that renders `<li role="status">{message}</li>` when `toast()` is called violates this by construction. Sonner shipped exactly that bug until issue #306 — *"ARIA live regions should always be present on screen so that screen readers can subscribe to their changes"* — which reported silent toasts in Windows Narrator and older iOS VoiceOver [[17]](https://github.com/emilkowalski/sonner/issues/306).

**2. `status` is the default; `alert` is the exception.** `role="alert"` implies `aria-live="assertive"` + `aria-atomic="true"`; `role="status"` implies `polite` + `atomic` [[8]](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1/). Assertive *interrupts the screen reader mid-sentence* and, per spec, assistive tech **may discard everything already queued** — so a chatty assertive toast can silently delete a polite message the user needed [[9]](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-2/). MDN: use `alert` only for urgent, time-sensitive information (session expiring, connection lost); otherwise use `status` [[7]](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role). Scott O'Hara's position is that a toast *is* a status message and belongs in `role="status"` (or `role="log"` if kept) [[10]](https://www.scottohara.me/blog/2019/07/08/a-toast-to-a11y-toasts.html). Radix went further and hard-codes `role="status"` for **all** toasts, with the reason in a source comment: *"Toasts are always role=status to avoid stuttering issues with role=alert in SRs"* — modulating urgency via `aria-live` instead [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx).

**3. Live regions cannot carry interactive content.** `alert`, `status` and `log` all map to live regions, so a screen reader *"will announce the raw text within, without any of the structure"* — an Undo button inside a toast is announced as the word "Undo", with no path to reach it [[11]](https://adrianroselli.com/2020/01/defining-toast-messages.html). Adrian Roselli's conclusion: if it has an interactive child, it should not be a live region and should not be a toast — move focus to it and make it persistent [[11]](https://adrianroselli.com/2020/01/defining-toast-messages.html). Scott O'Hara allows a toast action only if *"the contained action is also readily available outside of the toast, in the primary document"* [[10]](https://www.scottohara.me/blog/2019/07/08/a-toast-to-a11y-toasts.html). This is why [Base UI](https://base-ui.com/react/components/toast) and [React Aria](https://react-aria.adobe.com/Toast) render each toast as a **non-modal `dialog` / `alertdialog`** and put a *separate* hidden live region alongside it for the announcement [[31]](https://github.com/mui/base-ui/blob/master/packages/react/src/toast/viewport/ToastViewport.tsx) [[29]](https://react-aria.adobe.com/Toast) — the dialog holds the buttons, the live region holds the text.

## Auto-dismiss vs WCAG 2.2

| SC | Level | Text | Toast implication |
|---|---|---|---|
| [2.2.1 Timing Adjustable](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) [[1]](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) | A | User can turn off / adjust ×10 / extend with 20 s warning | An auto-dismissing toast is a content-set time limit → fails, **unless** the information is available elsewhere |
| [2.2.3 No Timing](https://www.w3.org/WAI/WCAG22/Understanding/no-timing.html) [[3]](https://www.w3.org/WAI/WCAG22/Understanding/no-timing.html) | AAA | "Timing is not an essential part of the event or activity" | APG: *"Avoid designing alerts that disappear automatically. An alert that disappears too quickly can lead to failure to meet… 2.2.3"* [[5]](https://www.w3.org/WAI/ARIA/apg/patterns/alert/) |
| [4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) [[4]](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | AA | Status must be programmatically determinable **without receiving focus** | This is what forces the live region — and forbids focus-stealing toasts |
| [2.4.11 Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) [[12]](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) | AA (new in 2.2) | Focused control must not be *entirely* hidden by author content | A bottom-right toast stack over a focused button/field is a straight AA failure — rarely tested |

**The escape hatch, and it's real.** SC 2.2.1's Understanding doc says *"Content that operates on a timer does not need to be time adjustable if there is an alternative that does not rely on a timer"* [[1]](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html). So a toast whose information is *also* reachable — an inline status, a notification centre, the updated row in the table — is compliant. A toast that is the **only** carrier of the information (the classic "Undo" or the only error report) is not. Whether SC 2.2.1 formally bites toasts at all has been an **open W3C question since 2019**: Patrick Lauke's `w3c/wcag#976` ⭐ 1.5k asks *"does a disappearing toast represent a timeout?"* and is still open with no working-group resolution [[2]](https://github.com/w3c/wcag/issues/976). Practitioner audits do not wait for it: an April 2026 shadcn/ui audit (WCAG 2.2 AA; VoiceOver, NVDA, macOS Safari / Windows Firefox+Chrome) flags Sonner's 4-second default as a 2.2.1 failure — *"For users with cognitive disabilities or slow readers, this is too fast"* — and recommends 8 s minimum plus a close button [[20]](https://thefrontkit.com/blogs/shadcn-ui-accessibility-audit-2026). React Aria's docs independently recommend **5 s minimum** and *"Only auto-dismiss toasts when the information is not critical, or may be found elsewhere"* [[29]](https://react-aria.adobe.com/Toast).

Roselli's fuller failure list for typical toasts: 1.3.2, 1.4.4, 1.4.10, 2.1.1, **2.2.1**, 2.4.3, 3.2.4, 4.1.2, 4.1.3 [[11]](https://adrianroselli.com/2020/01/defining-toast-messages.html).

## Keyboard: the toast you can see but cannot reach

Toasts must not steal focus — APG's keyboard interaction for `alert` is literally *"Not applicable"*, because *"it is crucial they do not affect keyboard focus"* [[5]](https://www.w3.org/WAI/ARIA/apg/patterns/alert/). But a toast rendered into a portal at the end of `<body>` is also **after** everything in tab order, and it may vanish before the user tabs to it. The industry answer is a **landmark + hotkey**:

| Library | Hotkey | Mechanism |
|---|---|---|
| [React Aria](https://react-aria.adobe.com/Toast) | **F6** / Shift+F6 | Toast region is a landmark; LandmarkManager cycles landmarks. On close, *"focus moves to the next toast… when the last toast is closed, focus is restored to where it was before"* [[29]](https://react-aria.adobe.com/Toast) |
| [Base UI](https://base-ui.com/react/components/toast) ⭐ 10.3k | **F6** | Global `keydown` force-focuses the viewport landmark [[31]](https://github.com/mui/base-ui/blob/master/packages/react/src/toast/viewport/ToastViewport.tsx) |
| [Radix](https://www.radix-ui.com/primitives/docs/components/toast) ⭐ 19.1k | **F8** | `VIEWPORT_DEFAULT_HOTKEY = ['F8']`, viewport is `role="region"` with an `aria-label` that *includes the hotkey* [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx); two sentinel focus-proxy spans reverse tab order so the newest toast comes first [[13]](https://sandroroth.com/blog/react-toast-component/) |
| [react-toastify](https://fkhadra.github.io/react-toastify/) ⭐ 13.4k | **Alt+T** (v11, Dec 2024) | `hotKeys: e => e.altKey && e.code === 'KeyT'` focuses the first `[tabIndex="0"]` toast [[24]](https://github.com/fkhadra/react-toastify/blob/main/src/components/ToastContainer.tsx) [[23]](https://github.com/fkhadra/react-toastify/releases) |
| [Sonner](https://sonner.emilkowal.ski/) ⭐ 12.6k | **Alt+T** | `hotkey = ['altKey','KeyT']`; container is `tabIndex={-1}` ("remove from normal navigation flow, only available via hotkey"), each toast `tabIndex={0}` [[18]](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx) |
| [react-hot-toast](https://react-hot-toast.com/) ⭐ 11k | **none** | Toaster renders plain `<div>`s; no hotkey, no `tabIndex`, no landmark [[26]](https://github.com/timolins/react-hot-toast/blob/main/src/core/toast.ts) |
| [notistack](https://notistack.com/) ⭐ 4.1k | **none** | No landmark, no hotkey [[28]](https://github.com/iamhosseindhv/notistack/blob/master/src/ui/MaterialDesignContent/MaterialDesignContent.tsx) |

⚠ Announcing the hotkey matters as much as having one: Radix and Sonner both interpolate the hotkey into the region's accessible name ("Notifications F8" / "Notifications alt+T") so a screen-reader user learns it exists [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx) [[18]](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx). A hotkey nobody is told about is not an affordance.

## Screen readers in practice

- **The mount-time swallow.** NVDA in particular does not announce a `role="status"` element that *appears* already containing text. Radix works around it by rendering the announce node's text **on the next animation frame** — the source comment is explicit: *"render text content in the next frame to ensure toast is announced in NVDA"* [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx). Sandro Roth's August 2025 teardown documents the same: *"If an element with `role="status"` is added to the page, its content will not be announced by NVDA"* — Radix therefore renders it empty first, then re-renders with content after a delay [[13]](https://sandroroth.com/blog/react-toast-component/).
- **Double announcement.** Composing one message from several DOM insertions makes screen readers *"make multiple separate message announcements"*; the practical fix when reusing a live region is to blank it and re-fill after ~350–500 ms [[9]](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-2/). Radix's announce portal keeps the announce text mounted for 1000 ms before removing it [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx).
- **Dropped announcements.** react-toastify's `role="alert"` toasts are *not announced at all* in Firefox+Orca (they are in Chrome+Orca); the issue quotes MDN's "do not dynamically add a populated `role=alert`" rule and remains **open** [[22]](https://github.com/fkhadra/react-toastify/issues/1122). Radix's `radix-ui/primitives#3634` (July 2025, v1.2.14, **open**) reports `aria-live="off"` landing on the `role="status"` element in the *official docs demo*, reproduced across Chrome, Safari and Firefox — *"its presence is not announced by screen readers"* [[14]](https://github.com/radix-ui/primitives/issues/3634). (The current `main` source sets `aria-live={type === 'foreground' ? 'assertive' : 'polite'}`, so if you're on Radix, pin-check your version [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx).)
- **Virtual cursor ≠ focus.** Screen-reader users reading a toast with the virtual cursor generate **no focus event**, so any "pause while focused" logic never fires for them — they are racing the timer like everyone else [[10]](https://www.scottohara.me/blog/2019/07/08/a-toast-to-a11y-toasts.html).
- **`aria-live` is advisory, not binding.** *"ARIA live region properties are only strong suggestions"* — browsers and AT may override them. Test the combination you ship, don't trust the attribute [[9]](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-2/).

## Pause behaviour and reduced motion

Pause-on-**hover** is a mouse feature. It does nothing for keyboard or screen-reader users. The accessible version is pause on **hover + focus + window blur + document hidden**.

| Library | Pause on hover | Pause on focus | Pause on blur / hidden | `prefers-reduced-motion` |
|---|---|---|---|---|
| Radix ⭐ 19.1k | ✓ | ✓ | ✓ [[16]](https://www.radix-ui.com/primitives/docs/components/toast) | via your own CSS (unstyled) |
| React Aria | ✓ | ✓ [[29]](https://react-aria.adobe.com/Toast) | ✓ [[13]](https://sandroroth.com/blog/react-toast-component/) | via your own CSS (unstyled) |
| Base UI ⭐ 10.3k | ✓ | ✓ [[30]](https://base-ui.com/react/components/toast) | ✓ [[30]](https://base-ui.com/react/components/toast) | via your own CSS (unstyled) |
| Sonner ⭐ 12.6k | ✓ | ✓ | ✓ (`isDocumentHidden` → `pauseTimer()`) [[18]](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx) | ✓ `@media (prefers-reduced-motion) { … transition: none !important; animation: none !important; }` [[19]](https://github.com/emilkowalski/sonner/blob/main/src/styles.css) |
| react-toastify ⭐ 13.4k | ✓ `pauseOnHover` | — (`pauseOnFocusLoss` = window blur, not element focus) [[21]](https://fkhadra.github.io/react-toastify/accessibility/) | ✓ | ✗ no reduced-motion query in shipped CSS [[24]](https://github.com/fkhadra/react-toastify/blob/main/src/components/ToastContainer.tsx) |
| react-hot-toast ⭐ 11k | ✓ only `onMouseEnter`/`onMouseLeave` on the container [[26]](https://github.com/timolins/react-hot-toast/blob/main/src/core/toast.ts) | ✗ | ✗ | ✗ |
| notistack ⭐ 4.1k | ✓ (MUI Snackbar `onMouseEnter`) [[28]](https://github.com/iamhosseindhv/notistack/blob/master/src/ui/MaterialDesignContent/MaterialDesignContent.tsx) | ✗ | ✗ | ✗ |

Sonner is the only one of the batch that ships its own reduced-motion guard — a notable inversion, since it is also the one with the most motion.

## The uncomfortable conclusion

Roselli's position — that a rich, actionable toast can't be made accessible and should be a persistent, focusable, non-modal region instead — is no longer fringe. **GitHub removed toasts from Primer's design system in late 2025 "because of their accessibility and usability issues"** [[11]](https://adrianroselli.com/2020/01/defining-toast-messages.html). The defensible 2026 pattern is:

1. Toast = **text only**, `role="status"`, injected into a pre-mounted region. No buttons.
2. Any action offered in the toast is **also** available in the page (the undone row still has an Undo control).
3. Errors that block the user are **not** toasts — they're inline, focus-managed messages.
4. Auto-dismiss ≥ 8 s, pausable on hover *and* focus, with a close button; or no auto-dismiss at all when the toast is the sole carrier of the information [[1]](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) [[20]](https://thefrontkit.com/blogs/shadcn-ui-accessibility-audit-2026).
5. Provide the landmark hotkey **and** name it in the region label [[15]](https://github.com/radix-ui/primitives/blob/main/packages/react/toast/src/toast.tsx).

If your toast has an Undo button and a 4-second timer, no library choice will save you.
