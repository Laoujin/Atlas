General note

The runtime dictates the choice more than features do. React 19 is a non-issue — all six work with it. The real axis is RSC, bundle, and lazy-loading. Next.js App Router / RSC → next-intl or Lingui; Vite SPA → Paraglide (smallest) or react-i18next (ecosystem).

Runtime-dictionary — load a JSON/ICU catalog, resolve keys through a lookup layer at runtime. Bundle scales with the catalog; RSC needs workarounds. Compile-time — emit typed functions ahead of time. Unused messages tree-shake; Server Components call plain functions, no React context.[1][7]
B

Two runtimes, two paths

Where the translation
resolves & what ships
Path 1 · Client

Vite SPA

No RSC — everything is client-side, hydrates normally. Axis = bundle + DX.

  1. 01 · Source

    Locale catalogs

    JSON / ICU / message files, one per locale, in the repo.

  2. 02 · Build (Vite)

    Compile vs. bundle

    Compile-time libs emit tree-shaken typed functions; runtime-dictionary libs bundle the catalog behind a lookup layer.

    Paraglide ⇢ ESM fns typesafe-i18n ⇢ codegen react-i18next ⇢ dict react-intl ⇢ ICU dict
  3. 03 · Ship

    One client bundle + lazy chunks

    Vite splits locales natively via dynamic import() — the initial bundle carries one locale, others load on demand as chunks.[11]

  4. 04 · Browser

    Hydrate → DOM

    All translation work happens in the client; the payload is what the axis in Detail A measures.

Smallest, catalog-independent: Paraglide — 47 KB where i18next ships 205 KB, and stays flat 200→1000 messages.[7] A real migration dropped ~40 KB of i18next to ~2 KB.[14]
⚠ Skip next-intl here — it isn't built for a standalone Vite SPA; the docs make no mention of non-Next.js usage.[4]
Path 2 · Server

Next.js App Router / RSC

RSC is the Next.js 16 default. Resolve on the server → ship translated HTML.

  1. 01 · Source

    Locale files or remote source

    File-based default assumes locales live in the repo — updates ride deployments unless you wire a remote source.[3]

  2. 02 · Server render

    Resolve in async Server Components

    Awaitable getTranslations (next-intl) or server useLingui reading a per-request instance from React cache — no use client.[4][8]

    next-intl ✓ native Lingui ✓ native react-i18next ⚠ createInstance react-intl ⚠ use client
  3. 03 · Output
    Zero translation JSfinal HTML · no hydration step for server strings
  4. 04 · Client islands

    use client — interactive bits only

    Client Components use the useTranslations / useLingui hook for the parts that need runtime state.[4]

Why RSC-native wins payload: Server Components send only rendered output — no component JS — so server-resolved strings ship nothing to the client.[16][3]
⚠ Lingui sharp edge: call setI18n() in every page and layout, not just the root; static rendering needs generateStaticParams for all locales.[8]
⚠ Run Next as a pure client SPA? The RSC advantage disappears — the Vite guidance applies.[17]

D

Specification by runtime

Pick the path first,
then the library
If the target is a

Vite SPA

  • ParaglideSmallest, catalog-independent bundle via compile-time tree-shaking.
  • react-i18nextThe deepest ecosystem — if you'll manage namespace splitting yourself.
  • typesafe-i18nWhen you want codegen type-safety. Vite handles all three's lazy locale chunks natively.
If the target is the

Next.js App Router

  • next-intlThe reference choice — async getTranslations, request-scoped config, 457 B server-only path.
  • LinguiThe alternative when you want one identical API across server + client.
  • react-i18next / next-i18nextReserve for migrating an existing Pages Router app — not greenfield.
